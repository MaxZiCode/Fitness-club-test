# Принятые решения

Разделение ответственности

Бизнес-логика сосредоточена в сервисном слое, поскольку основные сценарии затрагивают несколько сущностей и требуют согласованного выполнения последовательности действий. Например, создание брони включает проверку доступности занятия и абонемента, защиту от конкурентных запросов, изменение состояния нескольких сущностей, фиксацию транзакции и инвалидацию кэша.

Размещение такой логики в контроллерах смешало бы бизнес-правила с HTTP-обработкой и затруднило повторное использование и тестирование сценариев. 

Контроллеры остаются простыми: они отвечают за валидацию входных данных и формирование подходящего HTTP-ответа. Репозитории отвечают за получение и изменение данных. Такое разделение позволяет тестировать бизнес-сценарии независимо от HTTP-слоя, а поведение эндпоинтов проверять интеграционными тестами.

## Конкурентный доступ

Для предотвращения переполнения занятий используется явная блокировка строки занятия в PostgreSQL. Изменение абонементов также защищено блокировками. При одновременной работе с несколькими абонементами они блокируются в едином порядке, что предотвращает взаимные блокировки между конкурирующими операциями.

## Идемпотентность

Для повторных запросов сохраняется возможность воспроизвести первоначальный результат операции, даже если состояние записи позднее изменилось. Ключ идемпотентности хранится в виде SHA-256-хеша, что позволяет не ограничивать длину исходного ключа.

Если одинаковый ключ используется с разными данными запроса, возвращается `409 Conflict` с причиной `idempotency-payload-mismatch`.

## Лист ожидания

При освобождении мест применяется жадный алгоритм: выбирается самая старая запись, для которой хватает оставшихся мест. Поэтому более поздняя запись может быть обработана раньше, если более ранняя не помещается.

Продвижение очереди выполняется в той же транзакции, что и отмена брони. Для снижения риска взаимных блокировок абонементы текущего пользователя и подходящих кандидатов обрабатываются с единым порядком блокировок.

Записи очереди, получившие места, не удаляются: их статус меняется на `promoted`. Это сохраняет историю перехода из ожидания в активную бронь.

## Кэширование карточек

Для карточек используется Cache-Aside с версионированием в Redis. Версия пользователя позволяет инвалидировать все его карточки, а версия отдельной брони — конкретную карточку. При изменениях соответствующая версия увеличивается, поэтому последующие чтения не используют ключи со старой версией. Инвалидация выполняется после успешного коммита транзакции.

## Пагинация

Для постраничной навигации по расписанию используется непрозрачный для клиента `continuationToken`, содержащий курсор по времени начала занятия и его идентификатору. Это обеспечивает однозначную позицию продолжения даже при совпадении времени начала нескольких занятий.

## Тестирование

Эндпоинты и репозитории покрываются интеграционными тестами, сервисы — unit-тестами. Контроллеры отдельно не тестируются, поскольку отвечают только за валидацию входных данных и формирование HTTP-ответов.
